# Move CI from setup-java to mise Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Chorito moves every `setup-java` step to `jdx/mise-action`, with exact JDK versions in `.tool-versions`.

**Architecture:** Chorito's own workflows are the templates, so they change first and `Template` exposes the new steps. Chores then migrate other repos: `IdiomaticVersionFileChore` pins versions, `GitHubActionChore` rewrites workflows, a new chore edits poms, and `RenovateChore` keeps versions moving.

**Tech Stack:** Java 25, Maven, snakeyaml through `GitHubActionsWorkflowFile`, jsoup through `MavenPomFile`, JUnit 5, AssertJ, memoryfilesystem through `FileSystemExtension`.

**Spec:** `docs/superpowers/specs/2026-11-05-mise-ci-design.md`

**Worktree:** `~/Developer/chorito-main/ws/chorito-mise`, branch `ci/mise-chore`.

**Verify command for every task:** `./mvnw --batch-mode -P '!graal' test`. Expected: `BUILD SUCCESS`. Native builds are too slow to run per task; CI runs them in Task 8.

## Global Constraints

- Variable name, exactly: `SKIP_GRAALVM_NATIVE_IMAGE_BUILD`.
- `JavaVersions.GRAALVM = "25.0.5.0.3"`, `JavaVersions.TEMURIN = "25.0.5+8.0.LTS"`.
- `mise-action` pin: `jdx/mise-action@f5be966e4a917d54244728e6a5fdcd1d93a35e6c # v5.2.6`, with `cache: false` and `MISE_VERSION: 2026.11.1`.
- `actions/cache` pin: `actions/cache@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0`.
- No `mise.toml` or `mise.lock` anywhere.
- A second chorito run on any repo must produce no diff.
- Do not change anything in another repo before Task 8.
- Every commit message ends with `Claude-Session: https://claude.ai/code/session_01J1LocKCqNCgMfXDnbFA7vp`.

## Review Focus

- A `.tool-versions` with other tools beside `java`: only the `java` line changes.
- A `setup-java` step reading `src/.tool-versions`: it stays on `setup-java`, and its job gets no mise step.
- `pkl-config-java-native`: its exact innovation version, Truffle Renovate group and child-module `graal` profile all survive.
- A repo whose workflows no longer mention `graalvm`: it still counts as GraalVM, so a second run changes nothing.
- A non-GraalVM repo: it gets neither the skip variable nor the pom change, and a workflow that wrongly has the variable loses it.
- A Temurin repo with a 7 day minimum age: its JDK updates must not stay pending, so it gets the `java-version` package rule.
